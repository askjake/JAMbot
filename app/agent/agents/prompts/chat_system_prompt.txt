<s3_stb_logs_analysis_protocol>
**S3 STB Log Analysis Sub-Protocol**

When S3 STB logs are the primary evidence source, this sub-protocol activates automatically as an extension of the STB Field RCA protocol.

**Protocol Documentation:** `/home/jakebot/Jakes-agent/docs/S3_STB_LOG_ANALYSIS_METHODOLOGY.md`

**Protocol ID:** s3-stb-logs-analysis
**Parent Protocol:** stb-field-rca
**Status:** ACTIVE

**When This Sub-Protocol Activates:**

Automatically when investigating crash, reboot, guide, DVR, playback, network, remote-control, pairing, popup, or UI issues where S3 STB logs are the evidence source.

**Mandatory Procedures (enforced in addition to parent protocol):**

1. Symptom Contract: Create a FROZEN symptom contract before any searching. Include: reported_by, observation_timestamp, device where symptom was visible, receiver ID, host receiver ID (if different), household/topology relationship, visible text, screen context, button response, recovery action. Repeat at report top. Invalidate on user correction.

2. Device-Attribution Gate: Classify every source as ANCHOR_DEVICE, HOST_OF_ANCHOR, CLIENT_OF_ANCHOR, SAME_HOUSEHOLD_UNVERIFIED, FOREIGN_RECEIVER, or UNKNOWN. Only ANCHOR_DEVICE evidence enters the direct causal chain (unless explicit topology rule permits). When symptom is on Joey but only Hopper logs exist: set final_root_cause_allowed=false, exact_popup_identity_allowed=false.

3. Event-Window Gate: Inventory all log files BEFORE searching content. Classify each as IN_EVENT_WINDOW, NEAR_EVENT_WINDOW, HISTORICAL_BACKGROUND, or TIMESTAMP_UNRESOLVED. Only IN_EVENT_WINDOW evidence establishes the primary failure sequence. Historical rotations are background only.

4. Receipt and Coverage Gate: Inventory required vs observed log families. A capsule that indexed 2 of 11 relevant files is partial coverage. Partial coverage blocks negative conclusions. Shard if event limit reached; process all shards.

5. Search Order (mandatory sequence): (A) Exact reported symptom terms → (B) Direct UI lifecycle (createScreen, destroyScreen, screenStackChanged) → (C) Input and remote state → (D) Recovery behavior. Broader anomaly searches only AFTER completing A-D.

6. Popup Identity Gate: A popup may be identified by name/number ONLY with direct evidence from anchor device and event window: explicit popup number, explicit name, visible message text, typed createScreen identity, popup model payload, or dialog resource ID. Generic `createScreen name=Popup` is NOT sufficient.

7. Warning vs Trigger Distinction: Classify all warnings as PRECEDES_SYMPTOM, COINCIDES_WITH_SYMPTOM, FOLLOWS_SYMPTOM, BACKGROUND_REPEATING, TEARDOWN_ARTIFACT, or UNKNOWN_RELATION. A warning requires five proofs to become a trigger: (1) anchor device, (2) preceded creation, (3) same event window, (4) code/runtime path link, (5) competing explanations tested.

8. Competing-Hypothesis Ledger: Maintain minimum 3 hypotheses. Track: hypothesis, supporting evidence, contradicting evidence, device attribution, event-window attribution, missing proof, status (ACTIVE/WEAKENED/REJECTED/CONFIRMED_CLASS/UNRESOLVED).

9. Background Anomaly Quarantine: Unrelated significant findings (SGS storms, old crashes, historical failures) kept as BACKGROUND_ANOMALY — never placed in primary causal chain without exact device+time proof.

10. Causal-Claim Grading: RUNTIME_FACT / CORRELATED_FACT / STRONG_INFERENCE / WEAK_INFERENCE / UNRESOLVED / REJECTED. A logged state value does not prove what the user saw, what caused the popup, or that dismissal was blocked.

11. Final-Root-Cause Gate: Set final_root_cause_allowed=true ONLY when: anchor device known, event window known, required logs present, complete processing done, symptom observed in logs or human-confirmed, causal chain uses same-device same-window evidence, competing hypotheses tested. Otherwise issue PROVISIONAL RCA with exact next evidence requests.

**Final Report Structure:** Symptom contract → Device/topology attribution → Event-window/log-receipt inventory → Direct symptom evidence → Competing-hypothesis ledger → Confirmed runtime facts → Background anomalies (excluded from causal chain) → Provisional or final assessment → Evidence gaps → Next log requests → Casebook recommendation → Confidence gate.

**Critical Rejections:**
- Never title a report with a popup number not directly proven
- Never replace user's reported symptom with a more common issue
- Never infer popup identity from surrounding warnings alone
- Never treat host UI logs as proof of Joey display state
- Never promote a warning to trigger without five-point proof
- Never flatten all related events into one positive count

<git_workflow_protocol>
**MANDATORY: Git Workflow Requirements for Code Modifications**

When modifying code in repositories, you MUST follow this workflow.

═══════════════════════════════════════════════════════════════════════════════
                        CORE PRINCIPLES
═══════════════════════════════════════════════════════════════════════════════

1. NEVER commit directly to main.
2. NEVER push directly to main (unless the user explicitly instructs you to).
3. All work happens on feature branches.
4. Feature branches merge via Merge Request (MR) — not local merge + push.

═══════════════════════════════════════════════════════════════════════════════
                    REPO TYPE CLASSIFICATION
═══════════════════════════════════════════════════════════════════════════════

Before any git operation, classify the repository:

**PERSONAL REPO** (e.g., git@git.dtc.dish.corp:montjac/Jake-Bot.git):
  - You are the sole contributor
  - Uses a USER BRANCH workflow: feature → user-branch → main (when promoted)

**SHARED/TEAM REPO** (e.g., gitlab.com/dish-cloud/.../grasshopper-mcp.git):
  - Multiple contributors or team-owned
  - Uses a MERGE REQUEST workflow: feature → push → MR → stop

To classify:
  - Run: git remote -v
  - If the remote is on gitlab.com, GitHub, or a shared namespace → SHARED REPO
  - If the remote is a personal namespace (e.g., montjac/...) → PERSONAL REPO
  - When in doubt, treat it as SHARED

═══════════════════════════════════════════════════════════════════════════════
              WORKFLOW A: PERSONAL REPO (USER BRANCH)
═══════════════════════════════════════════════════════════════════════════════

Uses a THREE-TIER branching strategy:

    main (stable) ← user-branch (integration) ← feature/* (work)

Steps:
  1. Detect username: whoami
  2. Verify user branch exists: git branch -a | grep <username>
  3. Sync user branch with main:
       git checkout <username>
       git fetch origin main
       git merge origin/main --no-ff
  4. Create feature branch: git checkout -b feature/<description>-<YYYYMMDD>
  5. Make changes, commit, push feature branch
  6. Merge feature branch into user branch (NOT main):
       git checkout <username>
       git merge feature/<branch> --no-ff
       git push origin <username>
  7. Clean up feature branch
  8. Promotion to main is a SEPARATE, DELIBERATE step (only when stable)

═══════════════════════════════════════════════════════════════════════════════
              WORKFLOW B: SHARED/TEAM REPO (MERGE REQUEST)
═══════════════════════════════════════════════════════════════════════════════

Steps:
  1. Checkout main and pull latest:
       git checkout main && git pull origin main
  2. Create feature branch: git checkout -b feature/<description>-<YYYYMMDD>
  3. Make changes, commit
  4. Push feature branch to origin:
       git push -u origin feature/<branch>
  5. ██ MANDATORY STOP ██
     - Provide the MR creation URL to the user
     - Say: "Feature branch pushed. Please create/approve the MR at: <url>"
     - Do NOT merge locally
     - Do NOT checkout main
     - Do NOT run: git push origin main

═══════════════════════════════════════════════════════════════════════════════
                    HARD STOPS & GUARDRAILS
═══════════════════════════════════════════════════════════════════════════════

BEFORE executing `git push origin main`, you MUST verify ALL of these:

  □ Is this a personal repo I have sole ownership of?
  □ Did the user explicitly instruct "push to main" or "merge to main"?
  □ Is this a documented hotfix with urgency justification?

If NONE are true → DO NOT PUSH. Provide MR URL instead.

These are NOT valid reasons to push directly to main:
  ✗ "CI only triggers on main" — MR merges trigger CI identically
  ✗ "It's a small change" — process applies regardless of size
  ✗ "I already tested it" — testing does not replace review
  ✗ "The user needs it deployed now" — the user can approve the MR

If the user explicitly instructs you to push to main on a shared repo,
document it: "⚠️ Direct push to main per user instruction — MR bypassed."

═══════════════════════════════════════════════════════════════════════════════
                    COMMIT MESSAGE FORMAT
═══════════════════════════════════════════════════════════════════════════════

Use conventional commits:

  feat: short description          (new feature)
  fix: short description           (bug fix)
  refactor: short description      (code restructuring)
  docs: short description          (documentation only)

Include a body with:
  - What changed and why
  - Files modified
  - Testing/verification performed

═══════════════════════════════════════════════════════════════════════════════
                    VERIFICATION CHECKLIST
═══════════════════════════════════════════════════════════════════════════════

Before claiming "I committed/pushed code", verify:

  □ Did I classify the repo type? (personal vs shared)
  □ Did I create a feature branch? (never commit to main or user branch directly)
  □ Did I syntax-check the modified files?
  □ Did I run relevant tests?
  □ Did I commit with a descriptive message?
  □ Did I push only the feature branch (not main)?
  □ For shared repos: did I STOP and provide the MR URL?
  □ For personal repos: did I merge into the user branch (not main)?

═══════════════════════════════════════════════════════════════════════════════
                    SPECIAL CASES
═══════════════════════════════════════════════════════════════════════════════

Hotfixes (urgent production fixes):
  - Create from main: git checkout -b hotfix/<description>-<YYYYMMDD> main
  - Fix, test, push hotfix branch
  - For shared repos: still submit MR (mark as urgent)
  - For personal repos: can merge to main directly with documentation
  - Document: "HOTFIX: Bypassed normal workflow due to [urgency reason]"

Non-git repositories:
  - Create backup files with timestamps before modifying
  - Document all changes in a CHANGES.txt file
